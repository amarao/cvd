# CVD Basic Requirements

## Purpose

CVD (Create-Verify-Destroy) is a test tool for iaac (infrastructural code):

- existing Ansible/IaC projects with their own playbooks, inventory, and
  `ansible.cfg`;
- standalone Ansible roles;
- Ansible collections; and
- nested test scenarios with side effects and multiple verification suites.

CVD coordinates lifecycle actions. It does not prescribe how infrastructure is
provisioned or introduce its own infrastructure definition language.

## Core concepts

### Scenario

A **scenario** is the universal execution unit. A scenario can contain child
scenarios to arbitrary depth and can define any of these optional phases:

1. `dependency`
2. `create`
3. `prepare`
4. `converge`
5. `idempotence`
6. `verify`
7. child scenarios
8. `cleanup`
9. `destroy`

A child scenario inherits its parent's state and resources. It can add
resources and state values of its own. Its cleanup and destruction affect
only state owned by that child. It also can mask some resources of parent
scenario.

Side effect testing.

A child's `converge` phase can represent a side effect. Separate hard-coded
side-effect phases are therefore unnecessary. For example:

```text
scenario: default
  create
  prepare
  converge
  verify

  child: restart
    prepare
    converge       # restart side effect
    verify
    cleanup

  child: reconfigure
    prepare
    converge       # configuration side effect
    verify
    cleanup

  cleanup
  destroy
```

Examples of nested scenarios are as `baseline`, `side-effect`,
`upgrade`, or `failure-recovery`.

A given project may have multiple 'sibling' scenarios, each sibling scenario
is completely independent from other siblings (both for top-level scenarios
and for nested scenarios, siblings are dependent on parents, but not on
each other).

### Resource

A **resource** is anything created or discovered for duration of a scenario.
Examples include a virtual machine, container, Kubernetes object, a baremetal
server, or anything provisioner calls 'a resource'.

Every resource has:

- a stable identifier (for duration of scenario, including children scenarios);
- a type;
- an owning scenario; (responsible for creation/destruction)
- structured attributes;
- optional relationships to other resources; and
- optional sensitive attributes (e.g. passwords).

### state and View

The **state** contains resources, configuration, paths, and other
data available to lifecycle phases. state is available through views.

View is a concrete representation of resources and other data (specifics is defined
by the specific view). View is generated by CVD (built-in views)
and additional views can be provided by provisioner. User can also write custom
scripts, which accept one of CVD built-in views (json/yaml) and generate
a desired format.

The same state can produce more than one view.

Views are resources and path to them is stored in the state.

Examples of views:

(full state)

* json
* yaml

application specific views:

*  ansible inventory
* kube.conf
* clouds.yml

The intention of views is to provide converging/verifying tools with
enumeration of resources for a given scenario.

Children inherit the parent state and can reference parent resources.

### Test suite

A **test suite** is a named collection of verifier invocations. A scenario can
run one or more suites.

The initially supported verifier types are:

- `ansible`: run an Ansible verification playbook;
- `pytest`: execute pytest and interpret its test results; and
- `exec`: execute a command and interpret its exit status.

## Provisioning

CVD does not define what infrastructure `create` means. Provisioning is
delegated to a provisioner selected by the scenario.

Provisioners can be bundled, third-party, or project-local. Terraform,
Kubernetes, OpenStack, containers, and custom executables are possible
implementations.

### Minimal provisioner contract

A provisioner must support:

- `create`: create or discover resources and return a resource manifest; and
- `destroy`: destroy resources owned by the relevant scenario.

The definition of 'create' is up to provisioner, it can be allocation/deallocation
of resources from an existing pool, or create new (e.g. files, namespaces).

A provisioner can optionally support `dependency` phase (before create):
install or validate prerequisites, e.g. install ansible collections.

Provisioner input is opaque to CVD. Output is returned to CVD, and updated with
runtime information (phase, etc).

The provisioner contract must be available as a documented process protocol so
custom provisioners do not need to use CVD's implementation language. The exact
wire format and protocol versioning are deferred design decisions.

Input parameters for provisioner are set by CVD configuration for scenario,
and are saved into state. Provisioner reads state, creates required resources
and update state with information about created instances of resources.

## Ansible integration

CVD for Ansible must:

- use a project's existing `ansible.cfg`, inventory, playbooks, roles, and
  collections by default;
- allow each relevant path or setting to be overridden explicitly;
- preserve normal Ansible configuration precedence where practical;
- generate an inventory view from resources when requested;
- allow generated inventory data to be combined with project inventory; and
- expose resource and state data to playbooks in a documented form.

For role tests, CVD must make the role available under its expected Ansible role
name.

For collection tests, CVD must be able to install or link the collection into
an isolated Ansible collection path without requiring global installation.
Temporary isolation must not modify the source project.

## Execution and selection

The default root lifecycle is:

```text
dependency -> create -> prepare -> converge -> idempotence
           -> verify -> children -> cleanup -> destroy
```

(any element can be omited in scenario configuration)

The CLI must support running a given scenario;
- a scenario subtree; (the minimal chain of create/prepare/converge to get to run a given children scenario, e.g. if
  scenario A contains scenario A/1,  A/2, A/3, and user asked for A/3, then only create/prepare/converge is called for A
  and for A/3, but A/2 and A/1 are skipped).
- Ability to stop at a specific phase, and repeat it (e.g. to run specific prepare or converge, or verify for the second time)
- Specifically, a command to repeat the last phase, if cleanup code wasn't called before
- Ability to save current phase between CVD invocations and force transition to a given phase.
- Allow 'keep mode' which preserve state uncleaned in case of error or failure
- ability to cleanup state after operator done investigating/fixing the problem ('cleanup from current phase')

Example of scenario selectors:

```text
default
default/restart
default/instance_provision/second-reconfiguration
```

## Results, failures and errors

Each phase can be:

- `skipped`: was skipped by operator decision or scenario configuration.
- `pass`: all tests passed;
- `error`: a lifecycle action or verifier could not execute correctly.

Additionally, at any moment, CVD may panic (due to internal error),
in this case resources and state is in undefined state.

A verifier can report failed assertions as `fail`. A verifier crash,
invalid configuration, unreachable target, or malformed result produces
`error`. Fail is different from error, fails are saved and reported at the
end, they don't prevent to continue execution.

Any errors in create/prepare/cleanup/destroy are handled by errors (if
reported by corresponding code with non-zero exit status).

Every error retains its phase and origin, for example `Err(/default/reboot::prepare)`,
`Err(/default::converge)`, or `Err(/upgrade/version_1.2.3::verify)`.

Verifier failures are recored (failed verifier is not an error).
Failure in verification for a specific scenario does not prevent
continuation (except when marked as fails_are_fatal in scenario configuration).

Failures and errors are reported at the end of the CVD run, and if there was
an error or at least one fail, it cause non-zero exit code
(intendended to fail CI runs/automation).

Verifier can produce an additional report (JUnit, etc) which is stored
and reported at the end if needed.

Errors and failures also can be reported using additional CI mechanisms
(e.g. Github Annotiations).

## Cleanup and destroy semantics

Cleanup is stack-based and is best-effort:

- the active child is cleaned before its parent;
- a scenario's `cleanup` runs if scenario execution was entered and create was
  success or skipped, including after `converge`, `verify`, or child failure;
- `destroy` applies only to resources owned by that scenario;
- `destroy` may run even if create wasn't called (but this is unusual)
- a partial `create` may persist discovered/created resources so destruction can be
  attempted (provider specific).
- cleanup and destruction errors do not hide the primary failure;
- interactive 'keep mode' can suppress destruction or cleanups
- errors in cleanup/destroy are allowing all related cleanup/destroys to run as usual,
  but they cause skipping for all calls to children scenarios, verifies and converges.

## State and reporting

CVD persists enough state to support inspection, cleanup, and reruns:

- run identifier;
- last called scenario tree and stable selectors;
- resource information
- completed and failed phases;
- test results; and
- cleanup and destruction status.

Sensitive values are redacted from logs and reports.

## Initial non-goals

The initial version does not require:

- Molecule configuration compatibility or automatic conversion;
- a universal infrastructure definition language;
- a full inventory management system;
- a remote execution service or distributed scheduler;
- automatic flaky-test retries;
- a graphical interface;
- a plugin marketplace; or
- compatibility abstractions for every test framework.

A Molecule migration guide can be written separately.

## Deferred decisions

These choices require focused design work before implementation:

- configuration file syntax and schema;
- provisioner process protocol, manifest schema, and protocol versioning;
- resource-to-Ansible-inventory mapping and merge rules;
- persistence layout and secret handling;
- exact safe-phase and rerun rules after interrupted executions;
- plugin discovery and distribution; and
- aggregation rules for nested scenario results.
